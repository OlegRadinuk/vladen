# Compliance: резервное хранение заявок (leads.jsonl)

Проект: vladen-crimea.ru (ООО «ВЛАДЕН», ИНН 2317074414), ветка `fix-leads`.
Дата проверки: 2026-09-29. Проверял: compliance-агент (не юрист; финальные тексты должен вычитать юрист).

Изменение: `app/api/telegram/route.ts` + `lib/leads-log.ts` пишут каждую заявку (форма «Контакты» и чат-виджет)

### 1.4 Существующий поток: чат, optisphere и Anthropic — СКОРО
`app/api/chat/route.ts` проксирует переписку на `https://optisphere.tech/api/bots/vlad/chat`, дальше она уходит в Anthropic (США).
- В политике этот поток не описан (формулировка выше это исправляет).

- Если optisphere.tech — сервер Олега, а не ООО «ВЛАДЕН», Олег обрабатывает ПД по поручению оператора.
  Нужен пункт о поручении обработки (ч. 3 ст. 6 152-ФЗ) в договоре с ВЛАДЕН. То же относится к VPS `prod-main`,

## 2. Минимизация (ч. 5 ст. 5 152-ФЗ) — СКОРО

| Поле | Рекомендация | Обоснование |
|---|---|---|
| name, phone | Оставить | Суть заявки |
| source, page | Оставить, урезать `page` | Нужны для аналитики. В referer может быть `?utm...&yclid=...` — лучше хранить без query-строки (`URL.origin + pathname`) |
| ts, consent_timestamp | Оставить | Доказательство согласия |
| **ip** | **Оставить** | Стандартный элемент доказательства согласия (кто, когда, откуда) плюс антиспам. Уже заявлен в политике. Хранить в открытом виде в пределах срока хранения (хеш с солью обесценивает доказательство) |
| **ua** | Оставить, урезать до ~200 символов | Входит в тот же набор доказательств, уже заявлен, ценность небольшая. Можно убрать без вреда, если доказательство согласия не нужно. Решает клиент |
| calc | Оставить | Не ПД, контекст заявки |
| **chat** | **Урезать до 4000 символов** | В Telegram и так уходит максимум ~3700 символов. Хранить в резервной копии в 2 раза больше, чем реально использует менеджер, — избыточно. Переписка может содержать данные третьих лиц (адреса, имена родственников), лишнее хранить не нужно. Полностью убирать не надо: переписка — это суть лида из чата |

Замечание по коду для backend: `chat` режется по символам (`slice(0, 8000)`). При урезании до 4000
оставлять **конец** переписки (последние сообщения важнее), например `chat.slice(-4000)`.

## 3. Срок хранения и удаление — СКОРО

**Предложение:** 12 месяцев для `leads.jsonl` (сезонный цикл ремонта плюс повторные обращения).
Сейчас политика обещает «не более 3 лет», но ротации нет вообще, и файл растёт бесконечно. Это расхождение
между заявленным и фактическим. До внедрения ротации (п. 7 выше) формулировка «12 месяцев» будет неправдой,
поэтому текст политики и ротацию выкатывать вместе. Если ротация откладывается, в политике пока оставить «не более 3 лет».

### Реализация (описание, не внедрено)

**Вариант А (рекомендуется): помесячные файлы и cron с `find`.**
1. `leadsLogPath()` → `/var/www/vladen/data/leads-YYYY-MM.jsonl` (месяц по UTC из `new Date()`). Правка в 3 строки.
   Запись и удаление не пересекаются: текущий месяц никогда не удаляется, гонки нет.
2. Crontab пользователя, от которого работает pm2 (не root):
   ```
   # 03:30 ежедневно: удалить журналы заявок старше 12 мес. (+1 мес. запаса на текущий файл)
   30 3 * * * find /var/www/vladen/data -maxdepth 1 -name 'leads-*.jsonl' -mtime +395 -print -delete >> /var/www/vladen/data/purge.log 2>&1
   ```
   `purge.log` (без ПД, только имена файлов и даты) — это выгрузка из журнала для акта об уничтожении ПД
   (требования к подтверждению уничтожения — Приказ РКН от 28.10.2022 № 179). Раз в год при удалении
   оформлять простой акт: дата, какой файл, за какой период, способ — удаление с сервера.

**Вариант Б (без правки кода): logrotate** — `monthly`, `rotate 12`, `copytruncate`, `create 0600`.
Минус: у `copytruncate` есть окно, в котором строка, дописанная между копированием и обрезкой, теряется.
Для журнала, задача которого не терять лиды, это не подходит. Поэтому рекомендуется вариант А.

**Не забыть:**
- Бэкапы и снапшоты VPS (если включены в reg.ru): срок их хранения не должен превышать 12 месяцев,
  иначе ротация формальная.
- Удаление по запросу субъекта: node-скрипт или `jq` отфильтровывает строки по `phone` (нормализованному
  до цифр) во всех `leads-*.jsonl`, пишет во временный файл 0600 и делает `mv` поверх. Плюс ручное удаление
  сообщения в Telegram-чате. Срок — до 30 дней, ответ субъекту письменно.
- Права на файлы в варианте А: каждый новый месячный файл создаётся через `appendFile(..., { mode: 0o600 })` — уже так.

Оговорки (СКОРО):
1. Текст согласия — «Согласен на обработку персональных данных» — не говорит, что вместе с телефоном
   передаётся **вся переписка**. Предлагаемый текст:
   «Я даю [согласие на обработку персональных данных](/consent), включая текст этой переписки, и ознакомлен с [Политикой](/privacy)».

   это полезно и для доказательства: видно, какую форму и какой текст согласия видел пользователь.

Общее для обеих форм (СКОРО): с 01.09.2025 (изменения ст. 9 152-ФЗ, закон № 156-ФЗ) согласие
должно быть **оформлено отдельно** от других документов. Сейчас чекбокс ссылается только на Политику, а отдельного
текста согласия нет. Нужна страница `/consent`: оператор, перечень ПД, цели, действия, трансграничная передача (Telegram, Cloudflare, Anthropic),
срок действия согласия, способ отзыва. Чекбоксы ссылаются на неё, Политика остаётся второй ссылкой.

## 5. consent_timestamp — достаточно ли — СКОРО

Сейчас этого **недостаточно** для доказуемости:
- `consent_timestamp` генерирует **клиент** (`new Date().toISOString()` в момент отправки). Это не время
  отметки галочки, и его можно подделать. Доказательную ценность имеет серверный `ts` — он уже пишется.
- Сервер **не проверяет**, что согласие вообще дано: запрос без `consent_timestamp` принимается и сохраняется
  с `null`. Прямой POST в `/api/telegram` (бот, скрипт) создаёт запись ПД без согласия.
- Нет **версии текста**, на которую дано согласие. После смены политики (а она сейчас меняется) нельзя будет показать,
  с чем согласился человек в конкретной записи.

Что фиксировать дополнительно (передать backend):
| Поле | Откуда | Зачем |
|---|---|---|
| `consent: true` | клиент, явно | Факт галочки. Сервер отвечает 400, если не `true` |
| `consent_version` | константа в коде, например `"consent-2026-09-29"` | Какой текст согласия видел пользователь |
| `policy_version` | константа, например `"privacy-2026-09-29"` | Какая редакция Политики действовала |
| `source` (форма) | клиент: `contacts:<page>` / `chat` / `chat-lookbook` | Какую форму и какой текст чекбокса видел пользователь |
| `ts` (сервер) | уже есть | Авторитетное время |
| `ip`, `ua` | уже есть | Кто и откуда |

Плюс архив текстов: каждую редакцию `/privacy` и `/consent` сохранять неизменной (например в `spec/legal-archive/privacy-2026-04-20.md`
или в git-теге), чтобы по `consent_version` можно было предъявить точный текст.
